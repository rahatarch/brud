# Brud Code History Module Specification

## Overview

The History module is one of the core and biggest modules of Brud Code. It preserves the complete record of every Brud session executed in a workspace, enabling users to review past operations, inspect affected files, and revert to previous states.

## Core Principles

1. History is workspace-based. Each workspace has its own independent history stored locally.
2. Only files affected in a session are snapshotted. No unnecessary data is stored.
3. Two snapshots are taken per session: pre-patch and post-patch. This enables state travel to any point in the session timeline.
4. Diff-based storage is used for efficiency.
5. Terminal revert commands are preserved and executed on revert when specified.

## Architecture

### Core Package (Platform-Agnostic)

The core package contains:

- Session data types (HistorySession, HistoryOperation, SnapshotData)

## Data Model

### HistorySession

A single Brud session record.

Fields:
- sessionId: string (human-readable, e.g., BR-20260903-014)
- timestamp: ISO 8601 datetime
- originalPrompt: string (the exact Brud Prompt text given by user)
- status: success or failure
- operationCount: number of operations executed
- operationTypes: array of operation kinds
- filesAffected: array of file paths
- metadataUsed: object with operation metadata
- terminalCommands: array of commands executed (future)
- revertCommands: array of revert commands (future)

### SnapshotData

Pre-patch and post-patch file states.

Fields:
- sessionId: string
- snapshotType: pre or post
- files: map of file path to file content
- diffFromPrevious: unified diff from previous state

## Storage Format

Storage location: .brud/history/ inside the workspace root.

Directory structure:

.brud/history/
  sessions/
    BR-20260903-014/
      session.json
      pre.json
      post.json
      reverts.json
  delete-history.json
  cleanup.json

session.json contains the session metadata.
pre.json contains FULL content of affected files before the session.
post.json contains DIFFS of affected files relative to pre state.
reverts.json contains the revert history for the session (array of revert records).
delete-history.json contains the per-workspace audit log of all deleted sessions.
cleanup.json contains the retention cleanup log.

## Session ID Format

Human-readable format: BR-YYYYMMDD-NNN

Where:
- BR: Brud prefix
- YYYYMMDD: date of session
- NNN: sequential number for that day starting from 001

Example: BR-20260903-014 means the 14th session on September 3, 2026.

## Operation ID Format

Every operation within a session receives a unique identifier used for reference-based tracking.

Format: OP-YYYYMMDD-HHMMSS-NNN

Where:
- OP: Operation prefix
- YYYYMMDD: date of the operation
- HHMMSS: time of the operation
- NNN: sequential number within that second starting from 001

Example: OP-20260903-143021-005 means the 5th operation on September 3, 2026 at 14:30:21.

### Storage

The operationId is stored in the OperationResult object for each operation recorded in a session. It is generated by the `generateOperationId` function at the time the operation is recorded.

### Usage

Operation IDs are used as references by the revert history system. Instead of duplicating operation data, revert entries store operation IDs that reference the original operation records within the session. This ensures no data duplication and maintains a single source of truth for all operation data.

## Session ID Sequence

Session IDs follow the format BR-YYYYMMDD-NNN where NNN is a sequential number per day.

- getNextSequenceNumber checks existing session directories for the current date
- Starts at 001 and increments for each new session
- Prevents directory overwriting by ensuring unique IDs

Example: the first session on September 3, 2026 would be BR-20260903-001, and the 14th would be BR-20260903-014.

## Snapshot System

### Pre-Patch Snapshot (Full Content)

Taken BEFORE the session operations begin. Captures the FULL content of all files that will be affected by the session.

The pre-patch snapshot stores complete file contents. This serves as the reliable base state for long-term revert, regardless of how many sessions or manual edits happen afterward.

### Post-Patch Snapshot (Diff from Pre)

Taken AFTER the session operations complete. Stores a unified diff from the pre-patch state, not full content.

The post-patch snapshot is reconstructed by applying the diff to the pre-patch full content. This saves approximately 40% storage compared to storing both snapshots as full content.

### Storage Format

Pre-patch: files map with full file content for each affected file.
Post-patch: diffs map with unified diff for each affected file relative to pre-patch.

### Why Two Snapshots

The state before THIS patch may not be the original state of the workspace. Previous sessions may have already modified files. By storing both pre-patch (full) and post-patch (diff), the user can travel to any state in the timeline.

Example timeline:

Session 1: Pre-S1 (full) to Post-S1 (diff from Pre-S1)
Session 2: Pre-S2 (full) to Post-S2 (diff from Pre-S2)
Session 3: Pre-S3 (full) to Post-S3 (diff from Pre-S3)

User can revert to:
- Pre-S3 (undo Session 3) - write full content directly
- Post-S2 (state after Session 2) - apply diff to Pre-S2
- Pre-S2 (undo Session 2) - write full content directly
- Post-S1 (state after Session 1) - apply diff to Pre-S1
- Pre-S1 (original state) - write full content directly

### Why Full Pre + Diff Post

This hybrid approach provides:
- Reliability: Pre is always full content, so long-term revert works even if the file changes many times later
- Efficiency: Post is diff-based, saving storage
- Reconstructability: Post = Pre + diff
- Simplicity: Pre revert is direct write, Post revert is diff application

### Only Affected Files

Snapshots store ONLY files that were touched in that session. Not the entire workspace. This is storage-efficient and token-efficient.

## Terminal Revert Commands

When a session includes terminal commands, the user can specify revert commands in the Brud Prompt:

revert: npm run rollback

On revert, Brud executes these revert commands in addition to restoring file snapshots. This handles changes made by terminal commands that are not captured in file snapshots.

## Retention Policy

Default retention: 3 months (user-configurable in future Settings).

After the retention period, old sessions are automatically cleaned up.

Cleanup process:
1. Identify sessions older than retention period
2. Delete their snapshot directories
3. Remove their session.json entries
4. Log the cleanup action

## 7-Day Trash Protection

The 7-day trash protection provides a grace period before permanent deletion. When sessions are deleted, they are soft-deleted with flags rather than moved or immediately removed.

### Soft-Delete Approach

- Session stays in its original directory
- session.json gets flags: isDeleted, deletedAt, expiresAt, deletedBy, deleteReason
- Active sessions filtered by isDeleted !== true
- Trashed sessions: isDeleted === true && expiresAt > now
- Expired sessions: isDeleted === true && expiresAt <= now

### User Choice on Delete

- Delete modal has 7-day protection checkbox (checked by default)
- User can uncheck for permanent deletion
- Same for Wipe Out

### Retention Cleanup

Retention cleanup also goes to trash first with 7-day grace period.

### Restore

- Set isDeleted: false
- Clear deletion flags
- Session returns to active history

## Soft Delete History Array

Each session has a softDeleteHistory array in session.json that records every soft-delete and restore event infinitely.

### Array Structure

- action: soft_delete or restore
- at: timestamp
- by: user or system
- reason: manual_delete, manual_wipe, or retention_cleanup

A session can be soft-deleted and restored many times. The array records each event.

## Renewal Date

When a soft-deleted session is restored, a renewedAt date is recorded.

The retention cleaner uses renewedAt if present, otherwise createdAt, to determine session age.

This prevents the infinite delete-restore-delete loop where a restored session would be immediately deleted again because its original creation date is still old.

### Effective Age Calculation

- If renewedAt exists: age = now - renewedAt
- If renewedAt is null: age = now - createdAt

Each restore resets the retention clock for that session.

## Revert Flow

### Complete Operation Coverage

Revert is NOT limited to file content changes. Every operation type must be reversible. The History module records the operations performed in each session, enabling the revert system to perform the inverse action for each operation type.

### File Content Revert

For SEARCH_REPLACE and APPEND_FILE operations:
- Pre-patch revert: Write full pre-patch content
- Post-patch revert: Apply diff to pre-patch content to reconstruct post-patch content

### File Creation Revert

For CREATE_FILE operations:
- Pre-patch revert: Delete the created file if it still exists
- Post-patch revert: Write the created file content from post-patch snapshot

### File Deletion Revert

For DELETE_FILE operations:
- Pre-patch revert: Restore the deleted file from pre-patch snapshot
- Post-patch revert: Delete the file if it exists

### File Rename Revert

For RENAME_FILE operations:
- Pre-patch revert: Rename the file back from the new name to the original name
- Post-patch revert: Rename the file from the original name to the new name

### File Move Revert

For MOVE_FILE operations:
- Pre-patch revert: Move the file back from destination to source location
- Post-patch revert: Move the file from source to destination location

### File Copy Revert

For COPY_FILE operations:
- Pre-patch revert: Delete the copied file (destination)
- Post-patch revert: Recreate the copy from source content

### Directory Creation Revert

For CREATE_DIRECTORY operations:
- Pre-patch revert: Delete the created directory and all files inside it recursively
- Post-patch revert: Recreate the directory and empty files from the operation data

### Directory Deletion Revert

For DELETE_DIRECTORY operations:
- Pre-patch revert: Recreate the directory structure and restore all files from pre-patch snapshot
- Post-patch revert: Delete the directory if it exists

### Directory Move Revert

For MOVE_DIRECTORY operations:
- Pre-patch revert: Move the directory back from destination to source
- Post-patch revert: Move the directory from source to destination

### Structure Extraction Revert

For EXTRACT_STRUCTURE and CODEBASE_METADATA operations:
- No revert needed (read-only operations, no file changes)

### Revert with Terminal Commands

1. User selects revert
2. Brud restores file snapshots and reverses operations
3. Brud executes revert commands if specified in the session
4. Combined result reported to user

### Required Data for Complete Revert

The History session must store:
- operationTypes: what kinds of operations were performed
- operations: detailed operation data including paths, source, destination
- preSnapshot: full content of affected files before execution
- postSnapshot: diffs of affected files after execution

This data enables the revert system to perform the exact inverse action for every operation type.

## Revert History (Per-Session)

Each session tracks its own revert history in a dedicated file.

- Stored in the session directory as reverts.json
- Records: when reverted, target state (pre/post), reverted operation IDs, status
- Visible in the Session Detail page as a dedicated section
- Purpose: track all revert operations for a session
- Lives and dies with the session: deleting a session removes its revert history

Structure:
- timestamp: ISO 8601 datetime of the revert
- targetState: "pre" or "post"
- revertedOperationIds: array of operation IDs that were reverted (references operations in the session, no duplication)
- status: "success" or "failure"

### Reference-Based Design

RevertHistoryEntry uses operation IDs rather than file paths or duplicated operation data. This means:
- The `revertedOperationIds` array contains operation IDs (e.g., `["OP-20260903-143021-005", "OP-20260903-143021-006"]`)
- Each operation ID references the original operation record stored in the session
- No operation data is duplicated — the session remains the single source of truth
- When the session is deleted, the revert history is also removed since the referenced operations would no longer exist

## Individual Revert

Users can revert specific operations within a session rather than reverting the entire session. This provides fine-grained control over which changes are undone.

### UI

The Session Detail page displays an Operations section listing every operation performed in the session. Each operation entry includes a checkbox for selection.

- All revertable operations (file and directory operations) have enabled checkboxes
- Non-revertable operations (extract_structure, codebase_metadata) are shown with a disabled checkbox and visual indication that they are read-only

### Revert Selected

A "Revert Selected to Pre-Patch" and "Revert Selected to Post-Patch" button pair is shown at the top of the Operations section. These buttons are disabled until at least one operation is selected.

- Clicking either button triggers the standard revert flow for only the selected operations
- The revert is recorded in the session's revert history with the operation IDs of the selected operations
- The target state (pre or post) is recorded in the revert entry

## Individual Delete

Users can delete individual sessions from the History list without wiping the entire history.

### UI

Each session entry in the History list displays a trash icon button. Clicking it opens a simple confirmation modal.

### Confirmation Modal

The modal displays:
- The session ID being deleted
- A warning that this action cannot be undone
- Cancel and Confirm buttons

### Audit Logging

When a session is individually deleted, the event is recorded in delete-history.json with:
- reason: "manual_delete"
- The deleted session ID
- Timestamp of the deletion
- triggeredBy: "user"

## Revert Detail Page

Each entry in the Revert History section of the Session Detail page is clickable and opens a Revert Detail page.

### Data Display

The Revert Detail page shows exactly which operations were reverted in that specific revert action:
- Timestamp of the revert
- Target state (pre-patch or post-patch)
- Status (success or failure)
- List of operations that were reverted

### Operation Resolution

The page resolves each operation ID in the `revertedOperationIds` array against the session's stored operations:
- Operation ID → Operation type (e.g., SEARCH_REPLACE, CREATE_FILE)
- Operation ID → File paths involved
- Operation ID → Original operation metadata

### No Duplicate Storage

All operation data is retrieved by reference. The Revert Detail page never stores or caches operation data — it always reads from the session's operation records. This ensures consistency and prevents data drift.

### Navigation

- Clicking a revert entry → Revert Detail page
- Back button on Revert Detail page → Returns to Revert History section

## Delete History (Audit Log)

A per-workspace audit log maintained at .brud/history/delete-history.json.

Tracks:
- deletedCount: number of sessions deleted
- sessionIds: array of deleted session IDs
- timestamp: ISO 8601 datetime
- reason: retention_cleanup | manual_wipe | manual_delete
- triggeredBy: system | user

For manual wipes, the confirmationPhrase is recorded as proof of user confirmation.
Failed attempts are also recorded with:
- attemptedPhrase: the phrase the user typed
- expectedPhrase: the phrase required for confirmation

The delete history is:
- Not visible to users — internal audit only
- Purpose: legal protection and audit trail
- Kept forever (small metadata, never cleaned up)

### Event Types

The delete history records the following event types:

- soft_delete: session was soft-deleted (includes expiresAt for grace period tracking)
- restore: session was restored from trash
- permanent_delete: session was actually removed after the grace period expired

## Wipe Out History

The History tab provides a Wipe Out button for clearing all session history.

Process:
1. User clicks Wipe Out
2. Extreme confirmation prompt: user must type "DELETE ALL HISTORY" exactly
3. Failed attempts are logged in delete history with the attempted phrase
4. Successful wipe is logged in delete history
5. All session directories are deleted
6. Returns the count of deleted sessions

## UI Design

### History Tab (Management Window)

Chat-like list view showing sessions as conversation entries.

Each entry shows:
- Session ID
- Status indicator (success or failure)
- Timestamp
- Operation count and file count
- Brief description (from prompt or operation summary)

Sessions are grouped by date.

### Session Detail View

Clicking a session shows:
- Full session ID
- Timestamp
- Status
- Original Brud Prompt (verbatim)
- List of operations with metadata
- Files affected
- Revert options: Restore Pre-Patch State, Restore Post-Patch State

### Navigation Flow

The History tab uses a multi-level navigation model with these view states:

```
list → detail → reverts → revertDetail
revertDetail → back → reverts
reverts → back → detail
detail → back → list
```

- **list**: History tab showing all sessions grouped by date
- **detail**: Session Detail page for a selected session
- **reverts**: Revert History section within the Session Detail page
- **revertDetail**: Revert Detail page for a specific revert entry

Each view maintains a back button that returns to the previous level in the navigation stack.

### Visual Design

Follows Brud Code design system:
- Obsidian Black background
- Surface-2 for session cards
- Border for dividers
- Text-muted for secondary info
- Success green or error red for status indicators
